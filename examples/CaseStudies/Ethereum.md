## System Architecture

- Arsitektur: Layer 1 blockchain modular dengan pemisahan execution layer dan consensus layer (HIGH) [Ethereum.org - Nodes and Clients, https://ethereum.org/en/developers/docs/nodes-and-clients/; Consensus Specs, https://github.com/ethereum/consensus-specs]

## Consensus Mechanism

- Nama: Gasper (GHOST + Casper FFG) — Proof-of-Stake berbasis validator (HIGH) [Consensus Specs - Gasper, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/fork-choice.md; Ethereum.org PoS, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/]
- Validator Set: Dinamis, minimum 32 ETH stake per validator; activation/exit queue; >1 juta validator aktif (2024) (HIGH) [Beaconcha.in Stats, https://beaconcha.in/; Ethereum.org Staking, https://ethereum.org/en/staking/]
- Block Production: Slot-based (12 detik/slot); proposer dipilih via RANDAO + VRF; proposer membangun ExecutionPayload via Engine API (HIGH) [Consensus Specs - Block Proposal, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/block-proposal.md; Ethereum.org Block Production, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/block-proposal/]
- Attestation: Committee-based voting per slot; LMD-GHOST fork choice; source/target/checkpoint votes untuk finality (HIGH) [Consensus Specs - Attestations, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/attestation-processing.md; Ethereum.org Attestations, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/attestations/]
- Finality: Casper FFG — checkpoint justified (2/3 supermajority), lalu finalized (2/3 supermajority pada checkpoint berikutnya); ~12.8 menit untuk finality (2 epochs) (HIGH) [Consensus Specs - Finality, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/fork-choice.md#finality; Ethereum.org Finality, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/finality/]
- Slashing: Penalti untuk double proposal, double attestation, surround vote; ejection + partial stake burn; correlation penalty untuk mass slashing (HIGH) [Consensus Specs - Slashing, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/slashing.md; Ethereum.org Slashing, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/slashing/]
- Inactivity Leak: Penalty inactivity untuk chain tidak finalized; memastikan liveness recovery (HIGH) [Consensus Specs - Inactivity, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/fork-choice.md#inactivity-leak; Ethereum.org Inactivity Leak, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/inactivity-leak/]
- Sync Committees: 512 validator per periode (256 epoch) untuk light client verification; dipilih via RANDAO (HIGH) [Consensus Specs - Sync Committees, https://github.com/ethereum/consensus-specs/blob/dev/specs/altair/sync-committee.md; Ethereum.org Sync Committees, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/sync-committees/]
- Proposer-Builder Separation (PBS) / MEV-Boost: Proposer mengoutsourcing block building ke builder via relay; >90% blok melalui MEV-Boost (HIGH) [MEV-Boost Specs, https://github.com/flashbots/mev-boost-specs; Flashbots, https://flashbots.net/; Ethereum.org PBS, https://ethereum.org/en/roadmap/pbs/]
- RANDAO + VRF: Randomness untuk proposer selection dan committee shuffling; RANDAO reveal per epoch (HIGH) [Consensus Specs - RANDAO, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/randao.md; Ethereum.org RANDAO, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/randomness/]

## Security Model

- Validator Economics: 32 ETH minimum stake; slashing conditions (double sign, surround vote); inactivity leak; correlation penalty (HIGH) [Consensus Specs - Slashing, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/slashing.md; Ethereum.org Validator Security, https://ethereum.org/en/staking/validator-security/]
- Fork Choice: LMD-GHOST (Latest Message Driven GHOST) untuk block selection; aman di bawah asumsi synchronous network dan >2/3 honest stake (HIGH) [Consensus Specs - Fork Choice, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/fork-choice.md; Ethereum.org Fork Choice, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/fork-choice/]
- Finality Gadget: Casper FFG — accountable safety (jika finalized block ditolak, >1/3 stake slashable); plausible liveness (HIGH) [Casper FFG Paper, https://arxiv.org/abs/1710.09437; Consensus Specs - Finality, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/fork-choice.md#finality]
- Randomness: RANDAO (verifiable secret sharing) + VRF untuk proposer selection; biasable tapi unbiasable dengan single secret reveal (HIGH) [Consensus Specs - RANDAO, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/randao.md; Ethereum.org Randomness, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/randomness/]
- Client Diversity: 5+ execution clients, 5+ consensus clients; tidak ada client >2/3 market share (target); multi-client testnets (HIGH) [Client Diversity, https://clientdiversity.org/; Ethereum.org Client Diversity, https://ethereum.org/en/developers/docs/nodes-and-clients/client-diversity/]
- Formal Verification: K framework (EVM semantics), Certora, VeriSol, act untuk spec verification; Lighthouse menggunakan formal verification untuk critical paths (HIGH) [KEVM, https://github.com/kframework/evm-semantics; Certora, https://www.certora.com/; Lighthouse Verification, https://github.com/sigp/lighthouse/tree/master/verification]
- Fuzzing: Echidna, Foundry fuzzing, libFuzzer integration di klien (HIGH) [Echidna, https://github.com/crytic/echidna; Foundry Fuzzing, https://book.getfoundry.sh/reference/forge/fuzz; Geth Fuzzing, https://github.com/ethereum/go-ethereum/tree/master/fuzz]
- Audit Programs: Ethereum Foundation Protocol Security Grants; Immunefi bug bounty ($500k+ max); competitive audits untuk major upgrades (HIGH) [EF Security Grants, https://esp.ethereum.foundation/; Immunefi Ethereum, https://immunefi.com/bug-bounty/ethereum/; Consensus Specs Audits, https://github.com/ethereum/consensus-specs/tree/dev/audits]

## Known Technical Limitations

- Throughput: ~15-20 TPS base layer (simple transfers); ~100-200 TPS dengan blob data (EIP-4844); tidak cukup untuk global-scale tanpa L2 (HIGH) [Ethereum.org Scaling, https://ethereum.org/en/roadmap/scaling/; Dencun Impact, https://www.theblock.co/post/285000/ethereum-dencun-upgrade-live]
- Latency: Slot time 12 detik; finality ~12.8 menit (2 epochs); tidak cocok untuk real-time applications tanpa L2/optimistic confirmation (HIGH) [Consensus Specs - Timing, https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/beacon-chain.md#time-parameters; Ethereum.org Finality, https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/finality/]
- State Growth: World state terus bertambah (~200GB+ archive); history expiry (EIP-4444) belum live; statelessness roadmap belum tercapai (HIGH) [EIP-4444, https://eips.ethereum.org/EIPS/eip-4444; Ethereum.org State Expiry, https://ethereum.org/en/roadmap/state-expiry/; The Verge Roadmap, https://ethereum.org/en/roadmap/verge/]
- Client Diversity Risk: Geth execution client >50% market share historis; Prysm consensus client dominan awal; single-client bug risk (HIGH) [Client Diversity, https://clientdiversity.org/; Ethereum.org Client Diversity, https://ethereum.org/en/developers/docs/nodes-and-clients/client-diversity/]
- MEV / Censorship: PBS/MEV-Boost mengurangi tapi tidak eliminasi MEV; builder censorship (OFAC) pada ~20-30% blok; inclusion lists (EIP-7547) belum live (HIGH) [MEV-Boost Data, https://mevboost.pics/; Flashbots, https://flashbots.net/; EIP-7547, https://eips.ethereum.org/EIPS/eip-7547]
- Validator Centralization: Liquid staking tokens (Lido stETH >25% supply) menciptakan operator concentration; DVT (Distributed Validator Technology) adopsi belum masif (HIGH) [Lido Finance, https://lido.fi/; Rated Network, https://www.rated.network/; DVT, https://obol.tech/]
- Quantum Vulnerability: BLS12-381 signatures (KZG, validator signatures) vulnerable ke quantum; post-quantum roadmap (STARK-based, lattice) masih research phase (HIGH) [Ethereum.org Quantum Resistance, https://ethereum.org/en/roadmap/quantum-resistance/; Vitalik Quantum Post, https://vitalik.eth.limo/general/2023/10/31/quantum.html]
- Solo Staking Barrier: 32 ETH minimum, hardware/uptime requirements, technical complexity; mendorong pooling (HIGH) [Ethereum.org Solo Staking, https://ethereum.org/en/staking/solo/; Rocket Pool, https://rocketpool.net/]
- History Expiry: Full nodes menyimpan seluruh history (~1TB+ archive); EIP-4444 (history expiry) dan Portal Network belum production (HIGH) [EIP-4444, https://eips.ethereum.org/EIPS/eip-4444; Portal Network, https://github.com/ethereum/portal-network-specs]
- Gas Limit Constraints: Block gas limit ~30M (dapat di-naikkan validator); membatasi komputasi per blok; blob gas limit terpisah ~6M (HIGH) [Ethereum.org Gas Limit, https://ethereum.org/en/developers/docs/gas/; EIP-4844 Blob Gas, https://eips.ethereum.org/EIPS/eip-4844]

Behavioral Summary

Prioritas utama proyek:
1. Credible neutrality dan desentralisasi protokol (tidak memihak aplikasi, tidak sensor di base layer)
2. Skalabilitas via modular architecture (L2 execution + L1 settlement/DA) tanpa mengorbankan node accessibility
3. Keamanan ekonomi via Proof-of-Stake dengan validator set besar dan tersebar
4. Ekosistem pengembang terbuka dan berkelanjutan (tooling, grants, standards)
5. Evolusi protokol research-driven dengan backward compatibility ketat

Cara mengambil keputusan:
- Off-chain social consensus: EIP process → All Core Devs calls → Client team implementation → Validator signaling → Activation
- Research-first: EF research team produksi spec → Community review (ethresear.ch, Magicians) → EIP → Testnet → Mainnet
- Multi-stakeholder coordination: Tim Beiko (Protocol Support Lead) fasilitasi timeline client teams; tidak ada single decision maker
- Emergency response: Critical bug/exploit → Client teams patch dalam hari → Emergency hard fork jika perlu (2016 DoS, DAO)

Faktor paling memengaruhi keputusan:
1. Technical security dan correctness (formal verification, fuzzing, audit programs)
2. Client diversity readiness (tidak upgrade tanpa supermajority client ready)
3. Backward compatibility (tidak breaking existing contracts/users)
4. Credible neutrality principle (tidak sensor, tidak memihak)
5. Research maturity (spec finalized, tested, audited sebelum activation)

Pola evolusi:
- 2014-2015: Founding, crowdsale, Frontier launch, multi-client awal
- 2016: DAO crisis → governance precedent, DoS hardening
- 2017-2019: Metropolis upgrades, EVM precompiles, CREATE2, DeFi/NFT emergence
- 2020-2022: Beacon Chain → Merge (PoS transition), EIP-1559 fee market
- 2023-2024: Shanghai withdrawals, Dencun proto-danksharding, L2 dominance
- 2025+: Pectra (account abstraction, validator consolidation), Verge (verkle/stateless), Surge continued (PeerDAS)

Kekuatan utama:
- Distribusi token paling merata di L1 besar (no VC unlock overhang)

- Multi-client architecture production-proven (9+ client production)

- Credible neutrality track record (no protocol censorship despite pressure)

Kelemahan utama:
- L1 throughput terbatas (~15 TPS) bergantung L2 untuk scaling
- Finality latency 12.8 menit tidak cocok real-time apps
- State growth unbounded — history expiry, statelessness belum delivered
- Client diversity risk: Geth ~50% execution, Prysm/Lighthouse/Teku consensus concentration
- Validator centralization via LST (Lido >25%) tanpa protocol enforcement

- EF treasury transparency rendah (no real-time dashboard)

## Lessons Learned

Lesson 1: Fair launch tanpa VC unlock menciptakan distribusi token paling sehat dan menghindari overhang yang merusak price action jangka panjang
Lesson 2: Modular architecture dengan standardized interface (Engine API) memungkinkan multi-client diversity yang kritis untuk resilience
Lesson 3: Rollup-centric scaling (L2 execution + L1 settlement/DA) adalah path yang work untuk throughput tanpa sacrifice decentralization
Lesson 4: Off-chain social consensus governance (EIP + Core Devs + client signaling) bisa scale untuk protocol besar tanpa on-chain voting complexity
Lesson 5: Transparent on-chain economics (burn, issuance, MEV visible) membangun trust pasar dan legitimasi institutional
Lesson 6: Staged upgrade process dengan extensive testnet (devnet → testnet → shadow fork → mainnet) meminimalkan risk upgrade besar
Lesson 7: Credible neutrality principle (no protocol censorship, compliance di layer atas) mempertahankan legitimasi protokol di hadapan regulator
Lesson 8: Emergency response capability (patch dalam hari, emergency fork dalam minggu) critical untuk survival saat kritikal bug/exploit
Lesson 9: Grant-based ecosystem funding (EF ESP, Protocol Guild) sustainable untuk open-source development tanpa token inflation
Lesson 10: Backward compatibility ketat (additive upgrades, multi-tahun deprecation) melindungi existing users/contracts dari breaking changes

## Knowledge Summary

Strategic Principles:
1. Credible neutrality — protokol tidak sensor, tidak memihak
2. Modular architecture — execution/consensus split via Engine API
3. Research-driven roadmap — spec-first, transparent, community review
4. Multi-client diversity — every critical layer multiple implementations
5. Backward compatibility — no breaking changes without multi-year migration
6. L2-centric scaling — L1 settlement/DA, L2 execution
7. Infrastructure redundancy — no single RPC provider dependency
8. Community-driven tooling standards — EF grants, market adopts de facto standards

Success Factors:
1. Fair launch single public sale (no VC unlock overhang)
2. Multi-client architecture production-proven (9+ clients)
3. Largest developer ecosystem (6,200+ full-time devs)
4. Rollup-centric scaling delivered (L2 TVL $42.8B, 12-15M tx/day)
5. PoS transition + EIP-1559 burn → ultrasound money narrative
6. Institutional legitimacy (Spot ETF, CME derivatives, TradFi custody)
7. Emergency response proven (2016 DoS forks in weeks)
8. Transparent on-chain economics (real-time dashboards)

Failure Factors:
1. L1 throughput limited (~15 TPS) — dependent on L2
2. Finality latency 12.8 min — not suitable for real-time
3. State growth unbounded — history expiry/statelessness deferred
4. Client diversity risk — Geth ~50%, no protocol enforcement
5. Validator centralization via LST — Lido >25%, no enforcement
6. MEV/censorship ~20-30% blocks — inclusion lists pending
7. EF treasury transparency low — no real-time dashboard
8. Solo staking barrier high — 32 ETH minimum drives pooling
9. Informal governance — slow for controversies, no binding mechanism
10. Quantum vulnerability — BLS12-381 no migration timeline

Decision Framework:
1. Research & Specification (EF research → ethresear.ch/EIPs)
2. Community Review & EIP Process (draft → review → last call → final)
3. Client Implementation & Testing (devnet → testnet → shadow fork → mainnet)
4. Multi-Stakeholder Coordination (Tim Beiko facilitation, client readiness, validator signaling)
5. Activation & Monitoring (block/epoch trigger, post-upgrade dashboards)
6. Emergency Response (patch in days, fork in weeks if consensus affected)
