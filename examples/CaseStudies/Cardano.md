## System Architecture

Architecture: Dual-layer blockchain architecture comprising Cardano Settlement Layer (CSL) for value transfer and staking, and Cardano Computation Layer (CCL) for smart contract execution (HIGH) [Cardano Architecture, https://docs.cardano.org/architecture]
Layer 1: Cardano Mainnet (CSL + CCL integrated via Hard Fork Combinator) (HIGH) [Cardano Architecture, https://docs.cardano.org/architecture]
Layer 2: Hydra (Isomorphic State Channels) — off-chain scaling protocol with on-chain settlement guarantees (HIGH) [Hydra Docs, https://hydra.family/]
Layer 2: Mithril — stake-based threshold multi-signature protocol for fast sync and light client bootstrap (HIGH) [Mithril Network, https://mithril.network/]
Partner Chain: Midnight — privacy-preserving partner chain built on Polkadot SDK with ZK-proofs, interoperable with Cardano mainnet via bridge design (HIGH) [Midnight Network, https://midnight.network/]
Cross-chain Messaging: Planned via Midnight bridge and sidechain infrastructure (CIP-1694 governance actions for parameter changes) (MEDIUM) [CIP-1694, https://cips.cardano.org/cips/cip1694/]
Oracle Network: Charli3 (decentralized oracle network), Orcfax (fact-based oracle) — both native to Cardano (HIGH) [Charli3, https://charli3.io/; Orcfax, https://orcfax.io/]
Bridge: Native token bridge designs for Midnight and partner chains; no canonical Ethereum bridge operated by core entities (MEDIUM) [Midnight Docs, https://docs.midnight.network/]
Appchain: Partner chain model (Midnight) allows sovereign chains with shared security via Cardano stake pool operators (HIGH) [Midnight Announcement, https://iohk.io/en/blog/posts/2022/11/18/introducing-midnight/]

## Consensus Mechanism

Mechanism: Ouroboros Proof-of-Stake (family of protocols)
Variant: Ouroboros Praos (current mainnet since Shelley 2020-07-29) — semi-synchronous, adaptive security, stake-based leader election via VRF
Variant: Ouroboros Genesis — enables bootstrapping from genesis without trusted checkpoint
Variant: Ouroboros Chronos — clock synchronization assumptions
Variant: Ouroboros Leios — upcoming throughput-optimized design (pipelined block production, parallel validation)
Variant: Ouroboros Peras — fast finality gadget (2024 research)
Leader Election: Verifiable Random Function (VRF) — stake-proportional, private, unpredictable
Slot Duration: 1 second
Epoch Duration: 5 days (432,000 slots)
Security Model: Formal proofs in UC model / simulation-based; adaptive corruption; honest majority of stake assumed
Sources: (HIGH) [IOG Research Ouroboros, https://iohk.io/en/research/library/; Cardano Consensus, https://docs.cardano.org/architecture/consensus/]

## Execution Environment

Environment: eUTXO (Extended Unspent Transaction Output) model — not EVM, not WASM, not Move VM
Smart Contract Language: Plutus Core (typed lambda calculus, based on System F) — compiled from Plutus Tx (Haskell EDSL) or alternative languages (Aiken, Plutarch, Helios)
Transaction Validation: Two-phase — Phase 1: UTxO consumption/production rules + value preservation; Phase 2: Script execution (Plutus Core interpreter) with cost model (CPU/memory units)
Data Availability: On-chain (datum attached to UTxO, reference scripts via CIP-33 inline datums)
Deterministic Fees: Fee = a * size(tx) + b * execution_units + c * script_size (parameters governed on-chain)
Sources: (HIGH) [Plutus Docs, https://docs.cardano.org/plutus/; Cardano Architecture, https://docs.cardano.org/architecture]

## Security Model

Validator Set: Stake Pool Operators (SPOs) — ~3,000+ registered pools; active block producers determined by stake delegation and VRF
Consensus Security: Ouroboros Praos — adaptive security under honest majority stake assumption; formal proofs in Universal Composability framework
Transaction Validation: Deterministic script validation via Plutus Core interpreter; cost model limits (CPU/memory) prevent DoS
Script Integrity: Reference scripts (CIP-33) and inline datums (CIP-32) reduce attack surface; script hash in UTxO address binds logic immutably
Light Client Security: Mithril — stake-based threshold multi-signatures for certified state snapshots; security reduces to honest stake majority
Governance Security: CIP-1694 — Constitutional Committee (threshold multi-sig), DRep delegation, SPO voting; governance actions require constitutional compliance
Network Security: P2P gossip protocol (Diffusion/Pipelining via CIP-31); peer selection via ledger peer snapshots
Cryptography: Ed25519 (keys), VRF (leader election), Blake2b-256 (hashing), BLS12-381 (Midnight ZK)
Formal Verification: Protocol specs in Agda/Coq; properties proven (chain growth, chain quality, common prefix)
Sources: (HIGH) [IOG Research Library, https://iohk.io/en/research/library/; Cardano Consensus, https://docs.cardano.org/architecture/consensus/; Mithril Network, https://mithril.network/; CIP-1694, https://cips.cardano.org/cips/cip1694/]

## Known Technical Limitations

Limitation: eUTXO concurrency bottleneck — single UTxO can only be consumed by one transaction per block; causes contention for popular DEX pools (order book / AMM designs require batching or concurrency solutions like transaction batching, multiple UTxOs, or off-chain sequencing)
Source: (HIGH) [IOG Blog eUTXO Concurrency, https://iohk.io/en/blog/posts/2022/02/14/understanding-eutxo-concurrency/]

Limitation: Plutus script execution budget limits — fixed per-block CPU/memory limits (currently ~72M CPU, ~14M memory units per block); complex scripts may exceed budget requiring optimization or splitting
Source: (HIGH) [Plutus Cost Model, https://docs.cardano.org/plutus/cost-model/]

Limitation: No native account-based model — all state in UTxOs; requires off-chain indexers (Kupo, Blockfrost, Koios) for efficient querying; no native event/log system like EVM
Source: (HIGH) [Cardano Architecture, https://docs.cardano.org/architecture]

Limitation: Hydra Head requires all parties online for progress — liveness assumption; contestation period (configurable, typically hours) delays finality; fan-out requires on-chain settlement transaction
Source: (HIGH) [Hydra Docs Limitations, https://hydra.family/head-protocol/limitations/]

Limitation: Mithril snapshots require honest stake majority — trust assumption for light clients; snapshot frequency governed by protocol parameters
Source: (HIGH) [Mithril Security Model, https://mithril.network/doc/security]

Limitation: Midnight partner chain bridge design not yet finalized on mainnet — trust assumptions for cross-chain asset transfer under development
Source: (MEDIUM) [Midnight Docs Bridge, https://docs.midnight.network/bridges/]

Limitation: Governance parameter changes require constitutional compliance review by Interim Constitutional Committee — adds latency to protocol upgrades
Source: (HIGH) [CIP-1694 Governance Actions, https://cips.cardano.org/cips/cip1694/]

Limitation: No native EVM compatibility — sidechain/partner chain required for Ethereum smart contract portability (Milkomeda C1 sidechain exists but not core protocol)
Source: (MEDIUM) [Milkomeda, https://milkomeda.com/]

## Governance

Governance Model: On-chain Constitutional Governance (CIP-1694 / Voltaire Era) — three-body system: Constitutional Committee (CC), Delegated Representatives (DReps), Stake Pool Operators (SPOs)
Voting System: Stake-weighted voting (1 ADA = 1 vote weight) via delegation to DRep or direct SPO voting; governance actions require threshold approvals
Voting Power: Derived from active stake delegation (live stake snapshot at governance action submission epoch)
Delegation: ADA holders delegate voting power to DRep (CIP-1694) or auto-delegate to SPO; DRep registration on-chain; delegation changeable any epoch
Proposal System: Governance Actions submitted on-chain (parameter changes, treasury withdrawals, hard fork initiation, new constitution, CC member changes); require deposit (refundable if ratified)
Treasury Governance: On-chain treasury withdrawals via Governance Action; validated by Constitutional Committee (threshold multi-sig); enacted after voting period + enactment delay
Status: Live (Interim Constitutional Committee active 2024-06; Constitution ratified 2024-08; DRep registration open; first governance actions processed)
Sources: (HIGH) [CIP-1694, https://cips.cardano.org/cips/cip1694/]; (HIGH) [Cardano Governance Portal, https://gov.cardano.org/]; (HIGH) [GovTool, https://govtool.com/]; (HIGH) [Cardano Constitution, https://gov.cardano.org/constitution]

## Inflation / Deflation

Inflation Mechanism: Monetary Expansion (protocol-level minting) — fixed diminishing schedule per epoch; ~0.3% per epoch initially, decreasing monotonically; funds staking rewards (majority) and treasury (minority)
Emission Schedule: Hardcoded in protocol parameters; total reserve ~8.887B ADA at genesis; distributed over ~20+ years until ~2140 tail emission; formula: reserve * decay_rate per epoch
Burn Mechanism: tidak ada burn mechanism native protokol (tidak ada fee burn, tidak ada EIP-1555 equivalent); fee transaksi masuk ke reward pool + treasury, tidak dibakar
Buyback: tidak ada program buyback protokol; entitas komersial (IOG, Emurgo) mungkin melakukan pembelian pasar untuk treasury korporat terpisah tetapi tidak透明
Supply Reduction: tidak ada supply reduction mechanism; supply monotonically increasing hingga max supply 45B ADA tercapai (~2140)
Status: Live (monetary expansion active since Shelley 2020-07-29; no burn, no buyback)
Sources: (HIGH) [Cardano Monetary Policy, https://docs.cardano.org/cardano-components/cardano-token/monetary-policy/]; (HIGH) [IOG Research Monetary Policy, https://iohk.io/en/research/library/]; (HIGH) [CIP-1694 Parameter Change Governance, https://cips.cardano.org/cips/cip1694/]
